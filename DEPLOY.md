# Deploying AGS

The app is deployed to two hosts from the same `main` branch:

| Host | How it deploys | URL |
| --- | --- | --- |
| **Vercel** (primary) | Vercel's GitHub app, on every push to `main`; previews for every PR | the Vercel production URL / custom domain |
| **Cloudflare Workers** (backup) | GitHub Actions workflow `.github/workflows/deploy-cloudflare.yml`, on every push to `main` or by hand (Actions → "Deploy to Cloudflare" → Run workflow) | `https://ags.<your-account>.workers.dev` |

Either one can serve the app on its own if the other is down.

## Vercel

Environment variables (Vercel → Project → Settings → Environment Variables):

| Variable | Notes |
| --- | --- |
| `ANTHROPIC_API_KEY` | Server-side only. Powers readings and interpretations. |
| `FREE_ASTRO_API_KEY` | Server-side only. Chart calculation. |
| `NEXT_PUBLIC_SUPABASE_URL` | Public by design (RLS protects the data). |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | Public by design. |
| `SUPABASE_SECRET_KEY` | Server-side only. Needed by the Astro Study test (participants have no account). |
| `STUDY_OWNER_USER_ID` | Your Supabase user id (Supabase → Authentication → Users). The Astro Study test puts participants' charts and results in this account. |

## Cloudflare

Built with the OpenNext adapter (`@opennextjs/cloudflare`, pinned to 1.0.0,
the last line supporting Next 14). Config: `wrangler.jsonc`, `open-next.config.ts`.

GitHub → repository → Settings → Secrets and variables → Actions → New repository secret:

| Secret | Where to find it |
| --- | --- |
| `CLOUDFLARE_API_TOKEN` | Cloudflare → My Profile → API Tokens → Create Token → template **Edit Cloudflare Workers** |
| `CLOUDFLARE_ACCOUNT_ID` | Cloudflare dashboard → Workers & Pages → Account ID (right-hand side) |
| `NEXT_PUBLIC_SUPABASE_URL` | Same value as on Vercel |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | Same value as on Vercel |
| `ANTHROPIC_API_KEY` | Same value as on Vercel; copied to the Worker as an encrypted secret |
| `FREE_ASTRO_API_KEY` | Same value as on Vercel; copied to the Worker as an encrypted secret |
| `SUPABASE_SECRET_KEY` | Supabase → Project Settings → API Keys → **Secret keys** (`sb_secret_…`, or the legacy `service_role` key). Lets the background timer write readings while the phone is locked. Never put it anywhere else. |
| `STUDY_OWNER_USER_ID` | Same value as on Vercel: your Supabase user id, for the Astro Study test. |

The workflow stops with a clear message if one of the first four is missing.

### Background readings

"Generate all categories" queues the readings in `generation_jobs`; a
Cloudflare timer (`triggers.crons` in `wrangler.jsonc`, every minute) runs
`cloudflare-worker.mjs` → `scheduled` → `/api/jobs/run`, which writes them one
at a time on the server. It needs the `generation_jobs` migration and the
`SUPABASE_SECRET_KEY` secret; the timer's own password (`CRON_SECRET`) is
generated by the workflow on every deploy. Until both are set up, the page
generates in the browser instead.

Local commands: `npm run cf:build`, `npm run cf:preview`, `npm run cf:deploy`.

## Database changes

Migrations in `supabase/migrations/` are run by hand in the Supabase SQL
Editor, before merging the change that needs them (see `supabase/README.md`).

## Auth redirects

Supabase → Authentication → URL Configuration → Additional redirect URLs,
one entry per host:
- `https://<your-domain>/auth/callback` (Vercel)
- `https://ags.<your-account>.workers.dev/auth/callback` (Cloudflare)

## Private beta

The site has no sign-up: the landing page and the sign-in page collect
"keep me posted" emails through FormSubmit (sent to hello@maisontarot.com),
and every app page needs a signed-in session (readees' `/r/…` links stay
public).
- Supabase → Authentication → Sign In / Providers: turn off "Allow new users
  to sign up", so accounts can't be created by calling Supabase directly.
  Add testers from Authentication → Users → Add user.
- FormSubmit sends an "Activate Form" email after the first submission from
  the live site; until its link is clicked, submissions are not delivered.

## The Astro Study test (TASK-0013)

The test is taken on the Astro Study site (astrostudy.co.uk/test/); AGS is its back end. The site's
page calls the public routes `/api/study/start`, `/api/study/<id>` and `/api/study/<id>/answer`, which
answer pages from astrostudy.co.uk, www.astrostudy.co.uk and the GitHub Pages preview
(joanacodes.github.io). Optional: `STUDY_SITE_ORIGINS`, comma-separated, replaces that list (for
example to add the site's workers.dev address). A participant's chart goes into the library of the
account named by `STUDY_OWNER_USER_ID`, and their results appear on `/study` (signed in as that
account). It needs:

1. the `202610260007_study.sql` migration (Supabase SQL Editor, see `supabase/README.md`);
2. `SUPABASE_SECRET_KEY` and `STUDY_OWNER_USER_ID` on both hosts (tables above), plus
   `ANTHROPIC_API_KEY` and `FREE_ASTRO_API_KEY` as for readings;
3. the fake charts: on `/study`, "Prepare fake charts" (keep the page open a few minutes). Until at
   least one is ready the test answers "not open yet";
4. this app's address in the Astro Study site's `hugo.toml` (`[params.study] api`).

The full readings each participant gets are written by the background timer (Cloudflare), like
"Generate all categories".
